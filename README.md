# Proof Expansion：从证明简述到完整证明

## 1. 项目定位

本项目研究一种面向数学科研写作的辅助能力：

> 将研究者提供的定理、证明思路或证明骨架，扩写为结构完整、步骤可审阅、依赖可追踪的数学证明。

这里的“扩写”不是自动发现新定理，也不是把模型生成的文字直接当作正确证明。它服务于研究者已经拥有一定数学内容、但需要进一步整理、展开、核查和改写的阶段。

本项目暂时作为独立实验区域，位于 `数学科研实践/` 下，并与 `Leonard/` 平级。它不属于 Leonard 治理仓库，也不修改 Leonard、Shakespeare 或其他现有项目。

## 2. 为什么要单独建立区域

这个任务同时涉及数学内容、证明组织、学术写作风格和模型评测。如果直接放入 Leonard，容易混淆以下几类东西：

- Leonard 的产品治理与工程设计；
- Shakespeare 的候选学术写作能力；
- 某一个具体数学问题的研究材料；
- 模型能力测试与 Skill 效果测试；
- 教师提供的、可能需要只读保护的证明草稿。

单独建立本目录，可以让实验拥有自己的输入、输出、基准题、风格材料、评测记录和缺口记录，同时保持与其他研究项目的边界清楚。

## 3. 当前研究问题

核心问题不是：

> 模型能不能写出一份看起来完整的证明？

而是：

> 在模型本身已经足够强的情况下，一个专门的 Skill 是否能稳定改善证明展开的研究流程、可审阅性、缺口诚实性和个人写作风格控制？

因此，本项目必须区分两种能力：

### 3.1 模型本身的能力

包括：

- 理解定理和假设；
- 找到证明中的关键引理；
- 完成代数、分析或组合推导；
- 识别常见的证明策略；
- 生成连贯的数学文字。

### 3.2 Skill 带来的能力

包括：

- 按固定顺序核对定理、假设和目标；
- 将证明拆成可审阅的局部步骤；
- 明确每一步使用了哪些定义、引理或外部结果；
- 区分“已给出”“可由前文推出”“需要引用”和“尚未证明”；
- 遇到关键缺口时停止硬补，并报告缺口；
- 不擅自改变定理范围、假设、符号或证明目标；
- 按研究者授权的文章风格组织表达；
- 为研究者留下可修改、可追问、可复核的中间结构。

如果一个 Skill 只是让输出变长，却没有改善上述行为，就不能认为它有效。

## 4. 预期输入

一次证明扩写任务的输入原则上应包括：

1. **定理陈述**
   - 定理名称或编号；
   - 明确的对象、假设和结论；
   - 符号与术语约定。

2. **证明简述或证明骨架**
   - 证明策略；
   - 关键步骤；
   - 已知使用的引理、定理或计算；
   - 研究者已经确信的部分；
   - 尚未确定或只记得大致方向的部分。

3. **允许使用的依赖**
   - 本文前面已经证明的结果；
   - 明确允许引用的标准定理；
   - 指定的参考文献或原始资料。

4. **写作要求**
   - 目标语言；
   - 文章或讲义风格；
   - 详略程度；
   - 是否需要 LaTeX；
   - 是否需要附带证明依赖表和缺口说明。

5. **可选的风格样本**
   - 研究者自己的文章片段；
   - 经过授权的证明段落；
   - 术语、句式、段落结构和符号习惯。

风格样本只用于学习表达方式，不用于证明数学命题，也不自动构成可引用的数学来源。

## 5. 预期输出

一次合格的证明扩写至少应包含以下部分：

### 5.1 证明前检查

- 重述定理和全部假设；
- 列出证明目标；
- 标记证明中会使用的定义、引理和外部结果；
- 指出输入骨架中可能存在的歧义。

### 5.2 完整证明正文

- 按逻辑顺序展开每一步；
- 解释关键等式、不等式、构造和归纳步骤；
- 避免用“显然”“容易看出”“标准论证”掩盖关键推理；
- 在必要处说明为什么某一步满足前置条件；
- 保持符号、对象类型和结论范围一致。

### 5.3 依赖与状态标注

对每个关键步骤标记其来源，例如：

- `given`：研究者明确提供；
- `definition`：直接来自定义；
- `previously_proved`：来自此前已经证明的结果；
- `standard_result`：需要明确引用的标准结果；
- `derived`：由当前证明中的前面步骤推出；
- `conditional`：只有在额外条件成立时才成立；
- `unverified`：目前无法从输入中确认。

### 5.4 缺口记录

如果证明不能被完整推出，应记录：

- 缺口所在步骤；
- 缺少的假设、引理、计算或引用；
- 缺口为什么影响后续结论；
- 需要研究者补充或确认的最小信息；
- 在缺口解决前，哪些部分仍然可以保留。

### 5.5 研究者审阅清单

输出应方便研究者逐项检查：

- 定理陈述是否准确；
- 假设是否全部使用且没有被偷偷增加；
- 每个引理是否真的适用于当前对象；
- 证明是否循环论证；
- 是否把“存在性”误写成“构造性”；
- 是否把模型猜测误写成已知事实；
- 结论是否超出了原定理的范围。

## 6. 明确禁止事项

本项目中的证明扩写能力不得：

- 把流畅的文字当作数学正确性的证据；
- 虚构论文、作者、定理编号或出处；
- 把未证明的中间结论伪装成标准事实；
- 偷换定理中的对象、假设、系数、范围或符号；
- 在关键步骤缺失时用“显然”“类似可得”直接跳过；
- 把研究者尚未确认的想法写成最终证明；
- 将一次具体问题中的临时假设自动推广为通用方法；
- 将模型输出直接标记为 `proved` 或等价的权威状态；
- 在未经明确授权时读取、复制、修改或传播教师的证明草稿；
- 在未经授权时修改外部仓库或运行 Shakespeare。

## 7. 评测原则：证明 Skill 是否真的有效

由于基础模型可能已经很强，本项目采用对照实验，而不是只看单次输出。

### 7.1 对照条件

至少比较：

- **Baseline**：不使用专门 Skill，只给模型正常任务说明；
- **Skill**：使用证明扩写 Skill；
- 可选：**Style-only**，只加入文章风格要求，不加入证明流程约束。

模型、问题、输入材料和允许使用的资料应尽量保持相同。

### 7.2 测试材料

初期使用有标准答案、边界清楚、可人工核验的 established problems。测试题应覆盖不同证明结构，例如：

- 直接证明；
- 反证法；
- 数学归纳法；
- 构造性证明；
- 等价命题之间的转换；
- 含有一个关键中间引理的证明。

还应制作故意不完整的输入：

- 删除一个关键假设；
- 删除一个关键引理；
- 保留错误的证明跳步；
- 混淆相近的对象或映射方向。

### 7.3 评测维度

| 维度 | 核心问题 |
|---|---|
| 数学正确性 | 每一步是否真的成立？结论是否超范围？ |
| 假设保真度 | 是否完整使用原假设？是否偷偷添加或删除条件？ |
| 缺口诚实性 | 缺信息时是否明确报告，而不是编造？ |
| 可审阅性 | 研究者能否定位每个关键步骤和依赖？ |
| 结构稳定性 | 同类问题是否采用稳定、可预期的输出结构？ |
| 风格贴合度 | 是否符合研究者的文章风格而非默认模型腔调？ |
| 修改成本 | 研究者需要花多少时间修订到可用状态？ |

### 7.4 成功标准

Skill 只有在相对 Baseline 至少显著改善以下两项，并且不明显损害数学正确性时，才认为有初步效果：

- 缺口识别与诚实报告；
- 证明步骤的可审阅性；
- 假设和依赖的显式管理；
- 研究者风格的稳定控制；
- 研究者最终修订时间。

如果 Skill 只增加篇幅、模板或形式标记，却没有减少错误和修订成本，应删减或放弃。

## 8. 推荐工作阶段

### 阶段 0：建立规格

明确 Skill 的输入、输出、禁区、状态标签和失败处理方式。不写实现，不运行真实材料。

### 阶段 1：建立小型基准集

选择少量 established problems，为每题保存：

- 原始定理；
- 压缩后的证明骨架；
- 人工核验的参考证明；
- 常见错误；
- 缺口版本；
- 评分标准。

### 阶段 2：进行 Baseline/Skill 对照

在相同模型和相同输入上比较两种条件，记录原始输入、输出、模型版本、Skill 版本和人工评语。

### 阶段 3：加入文章风格

在证明流程有效后，再加入研究者文章样本，评测风格变化是否稳定、是否影响数学清晰度。

### 阶段 4：局部真实材料试验

只有在前几个阶段表现稳定，并且研究者明确授权后，才使用真实研究材料。优先选择一个局部引理，不直接处理整篇文章或完整教师草稿。

### 阶段 5：形成 Shakespeare 候选需求

实验结果只能提出 Shakespeare 的候选需求，例如：

- proof expansion；
- proof dependency ledger；
- gap-aware drafting；
- researcher review checkpoints；
- style-controlled academic writing。

这些结果不自动等于 Shakespeare 的实现、架构选择或产品采纳。
